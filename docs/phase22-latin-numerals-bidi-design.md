## Repository Audit

The audit covered `App.tsx`, all files under `src`, application-generated PDF HTML, Excel export/import, accessibility strings, analytics labels, settings/backup previews, and numeric input parsers.

### Current formatting paths

- `src/utils/formatters.ts` is the existing central number/currency entry point, but it constructs a new `Intl.NumberFormat` for every call and uses `ar-SY` without forcing `latn`.
- `src/utils/multiCurrency.ts` formats canonical USD cents manually and contains its own Arabic/Persian digit map.
- `src/utils/salesUiState.ts`, `src/utils/supplierAccounts.ts`, and `src/components/ProductFormModal.tsx` duplicate digit conversion and decimal/grouping normalization.
- Locale-driven number/date output appears in 21 shipping files. Direct calls include `Intl.NumberFormat`, `Intl.DateTimeFormat`, `toLocaleString`, `toLocaleDateString`, and numeric `toLocaleString`.
- Analytics implements separate percent, compact-axis, weekday, hour, and trend-date formatting.
- Exchange-rate change formatting is separate from the central formatter.
- Dates are formatted directly in cash sessions, expenses, rates, sales, customers, inventory, purchases, accounting, and PDF generators.
- Raw numbers also enter labels through template strings, direct React children, list counts, quantities, IDs, account codes, invoice numbers, and accessibility labels.

### Current report/export paths

Application-generated PDF/HTML paths are:

- Invoice
- Customer return receipt
- Purchase receipt
- Supplier purchase return
- Cash-session report
- Supplier account/payment/statement reports
- Customer account/payment/statement reports
- Accounting reports

The HTML documents already declare page direction, but numeric cells are not governed by one shared `direction:ltr; unicode-bidi:isolate` rule and several reports call Arabic locale formatters directly.

`src/utils/excel.ts` writes financial and quantity fields as numeric cells. That behavior must remain. Text identifiers, barcodes, references, and dates must remain canonical ASCII text when generated by Sarafy. Excel import is not a backup path and its business semantics remain unchanged.

### Current input paths

Numeric input is spread across product pricing, exchange rate, cashier/payment, invoice filters, customer and supplier accounts, expenses, inventory adjustments, purchases/returns, cash sessions, and accounting cash adjustments.

The current parsers accept some Arabic and Persian digits, but behavior differs:

- some treat comma as grouping;
- some treat comma as decimal;
- some accept the Arabic decimal separator;
- some UI handlers reject every non-ASCII digit before parsing;
- controlled inputs commonly retain the original digit glyphs instead of displaying normalized ASCII digits.

### Current direction paths

- Sarafy does not globally force `I18nManager`; it derives `rtl` from the application language and uses explicit row direction and text alignment.
- The shipping source currently contains 132 `row-reverse`, 53 `writingDirection`, and 150 `textAlign` occurrences.
- There are no `marginLeft`, `marginRight`, `paddingLeft`, `paddingRight`, `borderLeft`, or `borderRight` occurrences in `src`.
- Remaining physical `left`/`right` usage is concentrated in full-width overlays, charts, the segmented-control indicator, scanner overlays, snackbar bounds, fixed cart/footer bounds, and one locale-aware product-card badge. These are not automatically defects: chart coordinates and symmetric full-width bounds are physical by design; locale-relative badges require an explicit language branch.
- Shared components already mirror many semantic rows and directional chevrons. `ListItem` deliberately changes right/left chevrons by language.
- `SegmentedControl` maps semantic selection to a physical indicator index and must be tested in both directions to avoid double reversal.
- Horizontal filters use a mix of ordinary horizontal `ScrollView` and `FlatList inverted={rtl}`. Each must be verified visually rather than mechanically inverted.

### Main risks found

1. `ar-SY` can emit Arabic-Indic digits and Arabic separators in UI and PDFs.
2. Direct date and percent formatters bypass the central safety boundary.
3. Duplicated input normalizers disagree about comma semantics.
4. Raw template-string composition can reorder signs, units, UUIDs, barcodes, and references inside Arabic prose.
5. Generic `AppInput` follows prose direction even when its value is numeric.
6. Raw numeric React children such as stepper values can bypass output normalization.
7. Creating `Intl` objects in list-row renders is unnecessary overhead.

## Numeral Policy

All application-controlled numeric output uses:

- digits: `0-9`
- grouping separator: `,`
- decimal separator: `.`
- negative sign: leading ASCII `-`
- percent examples: `25%`, `12.5%`
- date/time digits: Latin digits while preserving the current Gregorian/localized layout

Arabic and English share the same numeral glyphs and separators. Language still controls prose, labels, localized month/weekday names, and overall layout direction.

Identifiers are not quantities. UUIDs, invoice/journal/reference numbers, account codes, barcodes, and phone numbers remain canonical strings without locale grouping or digit substitution.

## Central Formatting Design

`src/utils/formatters.ts` will become the single presentation boundary and expose repository-appropriate helpers for:

- integer and decimal quantities;
- SYP and USD display;
- canonical USD cents;
- signed values and percentages;
- exchange rates;
- date, time, and date-time;
- identifiers/references and bidi isolation.

All `Intl.NumberFormat` and `Intl.DateTimeFormat` instances will explicitly request `numberingSystem: 'latn'`. Arabic formatters will use an Arabic locale for language-sensitive words but Latin digits and the standard punctuation policy. Every formatted result will pass through a pure ASCII digit/separator safety boundary where applicable.

Stable formatter instances will be cached by locale and a bounded options key. Render code will not construct a new formatter for every list row. No database queries or N+1 work are introduced.

## Output Normalization

A pure shared helper will map both Arabic-Indic and Persian digits to ASCII:

```text
٠١٢٣٤٥٦٧٨٩ → 0123456789
۰۱۲۳۴۵۶۷۸۹ → 0123456789
```

It is a presentation safety boundary, not a database migration. It will not rewrite arbitrary user-authored prose, stored notes, names, snapshots, UUIDs, or backup payloads.

## Input Normalization

One shared input normalizer will accept Latin, Arabic-Indic, Persian, and mixed digits. Controlled numeric fields will store/display the normalized ASCII text immediately.

The normalizer distinguishes syntax by field contract:

- integer/SYP/quantity fields: remove accepted grouping separators and spaces, reject decimal content;
- decimal/USD/rate fields: normalize `.` and Arabic decimal `٫` to `.`, accept only one decimal separator, and treat grouping separately rather than guessing;
- signed opening/adjustment fields: preserve only a valid leading `-`;
- barcode/reference/phone search: normalize digit glyphs only, with no grouping or numeric coercion.

The current business parsers keep their exact bounds, precision, integer-safety, rounding, and validation rules. They consume normalized text instead of maintaining private digit maps.

## Bidi Isolation

Arabic prose remains RTL; numeric and technical tokens remain LTR.

Preferred React Native representation:

- separate nested `Text` nodes or dedicated numeric/reference components;
- shared numeric style with `writingDirection: 'ltr'`, tabular figures, and alignment selected for the field role;
- locale-directed container placement independent of token direction.

When a plain composed string is unavoidable, centralized helpers may wrap technical tokens with Unicode LRI/PDI. Accessibility labels must use clean normalized text and should not contain invisible controls unless required for correct spoken order.

No manual character reversal, global LTR forcing, scattered LRM/RLM insertion, or business-string mutation is permitted.

## Alignment and Layout Policy

- Prose uses application-language start alignment: right for Arabic, left for English.
- Numeric entry content is always LTR. Its field can remain in the locale-relative form position.
- Numeric table cells are internally LTR with predictable alignment; table column semantics remain independent.
- Semantic rows use explicit `row`/`row-reverse` only once. Existing application-language layout remains the authority because global `I18nManager` forcing is not used.
- Semantic directional icons mirror individually. Back/forward/next/previous and navigation chevrons mirror; camera, barcode, search, plus/minus, currency, edit, delete, calendar, clock, check, close, upload, and download do not.
- Physical chart coordinates, symmetric full-width overlays, and scanner targeting geometry remain physical. Locale-relative badges and anchored actions use explicit locale mapping or start/end semantics where supported.
- Horizontal collections are verified individually for initial position, visual order, and accessibility order. React child order must not be reversed merely to obtain visual RTL.

## Shared Component Strategy

Foundation changes precede screen-specific fixes:

1. central output/input/bidi utilities;
2. shared numeric/reference styles or components;
3. `AppInput` support for numeric/technical content that normalizes live and renders LTR;
4. `MonetaryValue`, `QuantityStepper`, labels/counts, chips, list rows, modal summaries, and accessibility-value strings;
5. screen-specific direct locale calls and composed strings;
6. PDF HTML numeric spans/cells;
7. Excel-generated text fields without changing numeric cell types.

This order minimizes duplicated fixes and makes remaining exceptions auditable.

## PDF Policy

Every generated HTML document will declare page direction by language and a shared numeric class equivalent to:

```css
direction: ltr;
unicode-bidi: isolate;
font-variant-numeric: tabular-nums;
```

Numeric and reference cells/spans use that class. Arabic prose remains RTL. Column order follows report semantics and is not reversed merely because numeric cells are LTR. Page numbers, dates, times, signed values, decimals, barcodes, and references must contain only Latin digits.

## Excel Policy

True numeric data remains numeric. Phase 22 does not stringify money, quantities, rates, or accounting values. Generated textual identifiers and references stay ASCII. Input digit normalization may be reused when importing fields already defined as numeric, without changing Excel import or backup semantics.

## Search Policy

Numeric/reference-like search terms normalize digit variants before comparison. Arabic text remains unchanged. Search normalization must support `123`, `١٢٣`, and `۱۲۳` matching the same canonical numeric/reference target without locale-formatting arbitrary identifiers.

## Accessibility Policy

- Numeric visual tokens and accessibility labels use Latin digits.
- Amounts, dates, references, barcode values, and signed deltas remain logically readable.
- React tree order stays semantic; styling handles visual RTL.
- Existing labels, roles, states, and touch targets are preserved.
- Numeric inputs expose LTR content without changing Arabic label direction.
